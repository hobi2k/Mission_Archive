# 미션 16 요약 보고서

## 1. 실험 개요

- 팀/이름: 1팀 안호성
- 사용 모델: `qtranslator_1.7b_v2` (Qwen3-1.7B 기반 자체 훈련 한일 번역 모델)
- 실험 목표:
  - 학습된 LLM을 `.pth`, 양자화 `.pth`, `.onnx` 형식으로 변환
  - 변환된 각 포맷이 실제 추론에 사용 가능한지 검증
  - Hugging Face 원본 모델, `.pth`, 양자화 `.pth`, ONNX 간 추론 시간 차이를 비교

## 2. 제출 산출물

- 모델 추출 코드: `modeling.ipynb`
- 모델 추론 코드: `inference.ipynb`
- 요약 보고서: `미션16_1팀_안호성_요약보고서.pdf`

## 3. 모델 추출 결과

저장 파일은 과제 요구사항에 맞춰 아래와 같이 생성했다.

- `mission_16_qtranslator_1.7b_v2.pth`
- `mission_16_qtranslator_1.7b_v2_quantized.pth`
- `mission_16_qtranslator_1.7b_v2.onnx`

파일 용량(MB):

| 모델 형식 | 파일명 | 용량(MB) |
| --- | --- | ---: |
| PTH | `mission_16_qtranslator_1.7b_v2.pth` | 6563.60 |
| PTH Quantized | `mission_16_qtranslator_1.7b_v2_quantized.pth` | 2828.51 |
| ONNX + external data | `mission_16_qtranslator_1.7b_v2.onnx` + `.onnx.data` | 6568.74 |

관찰 결과:

- 동적 양자화(`torch.quantization.quantize_dynamic`)를 적용한 `.pth`는 원본 `.pth` 대비 용량이 크게 감소했다.
- ONNX는 본체 `.onnx`만 보면 작게 보일 수 있지만, 실제 가중치는 외부 데이터 파일 `.onnx.data`에 저장되므로 반드시 합산해서 확인해야 한다.

## 4. 추론 실험 설정

- 비교 대상: `hf`, `pth`, `pth_quant`, `onnx`
- 태스크: 한국어 -> 일본어 번역
- 프롬프트 형식:
  - `### Instruction:`
  - `### Input:`
  - `### Output:`
- 평가 데이터:
  - 직접 구성한 번역 샘플 5개 사용
- 실행 환경:
  - 형식별 비교 일관성을 위해 모든 방식은 CPU 기준으로 측정

## 5. 추론 결과

샘플별 결과를 확인한 결과, 네 가지 방식 모두 전반적으로 유사한 번역을 생성했다.  
형식별 평균 추론 시간은 아래와 같았다.

| 방식 | avg_sec | min_sec | max_sec |
| --- | ---: | ---: | ---: |
| `pth_quant` | 0.8936 | 0.587 | 1.109 |
| `pth` | 1.8774 | 1.263 | 2.627 |
| `hf` | 1.9756 | 1.257 | 2.523 |
| `onnx` | 3.3624 | 1.885 | 5.333 |

해석:

- 이번 실험에서는 `pth_quant`가 가장 빨랐고, ONNX가 가장 느렸다.
- 하지만 이것만 보고 "ONNX가 원래 가장 느리다"라고 결론내리면 안 된다.
- 이번 ONNX 추론은 `onnxruntime` 세션 위에서 토큰을 한 개씩 붙이는 수동 greedy decoding 방식으로 구현했다.
- 이 구현은 `past_key_values`(KV cache)를 사용하지 않기 때문에, 새 토큰을 생성할 때마다 전체 시퀀스를 다시 계산한다.
- 반면 Hugging Face `generate()`는 내부 최적화 경로를 사용할 수 있으므로, 이번 시간 비교는 "포맷 자체의 절대 속도"가 아니라 "현재 구현 방식까지 포함된 실험 결과"로 해석해야 한다.

## 6. 디버깅 및 오류 해결

이번 미션에서 주요하게 정리한 오류는 다음과 같다.

### 6-1. ONNX export 중 opset 17 변환 실패

- 로그:
  - `Failed to convert the model to the target version 17 using the ONNX C API`
  - `Assertion 'node->hasAttribute(kaxes)' failed`
- 원인:
  - `torch.onnx.export(..., opset_version=17)` 과정에서 일부 연산 그래프를 17로 다운컨버전하지 못했다.
- 해결:
  - 로그 마지막에 파일 저장이 완료된 것을 확인했고, 실제 ONNX Runtime 추론으로 동작 여부를 검증했다.
  - 따라서 치명적 추출 실패가 아니라 버전 변환 경고로 분리해 해석했다.

### 6-2. ONNX checker에서 `EncodeError: Failed to serialize proto`

- 원인:
  - 외부 데이터(`.onnx.data`)를 쓰는 대용량 ONNX 모델을 객체 상태로 `onnx.checker.check_model(onnx_model)`에 넘기면 내부 직렬화에서 실패할 수 있다.
- 해결:
  - 모델 객체 대신 파일 경로를 넘기는 방식으로 수정:
  - `onnx.checker.check_model(cfg.onnx_path.as_posix())`

### 6-3. ONNX 파일 용량이 비정상적으로 작아 보이는 문제

- 원인:
  - `.onnx` 본체만 보면 수 MB 수준으로 보일 수 있으나, 실제 가중치 대부분은 `.onnx.data`에 저장된다.
- 해결:
  - 보고서와 노트북 모두 ONNX 본체와 external data를 합산한 총 용량으로 표기하도록 수정했다.

## 7. 결론

- `.pth`, 양자화 `.pth`, `.onnx` 세 가지 형식으로 모델을 성공적으로 저장했다.
- `inference.ipynb`를 통해 Hugging Face 원본 모델, `.pth`, 양자화 `.pth`, ONNX 모두 추론이 가능함을 확인했다.
- 용량 측면에서는 양자화 `.pth`가 가장 유리했다.
- 시간 측면에서는 이번 구현 기준 `pth_quant`가 가장 빨랐고 ONNX가 가장 느렸지만, ONNX는 KV cache 미사용 수동 decoding 구현이라는 제약이 있으므로 일반적인 ONNX Runtime 성능과 동일시하면 안 된다.
